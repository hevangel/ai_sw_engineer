## Findings

- **STA flag deviation (potential RTL/oracle defect, flagged).** M68PRM
  Table 2-1 documents STA as setting N, Z and clearing V. Neither the
  project oracle nor the RTL updates CC on the STA store cycle (RTL
  `S_WR: state <= S_FETCH;` with no CC update; the ISS `sta` path sets no
  flags). The vector replay cannot detect this (every STA in the ISA
  program is followed by flag-re-establishing setup ops, and
  same-value stores make N/Z agree; only V could differ and the ISS
  defines the records). This core follows the project contract and
  records it as ASSUMPTION (M6800-A3) in `spec/isa.md`; worth confirming
  against real-silicon traces under
  [ai_engineer#43](https://github.com/hevangel/ai_engineer/issues/43).
- Two real bugs were caught by the replay during development and fixed:
  STS/STX flag updates were initially missing from the store path, and
  CBA initially skipped its N/Z update. The trigger harness initially
  mis-mirrored the RTL testbench's countdown semantics (Verilog
  nonblocking: the action fires when the OLD countdown is 1).

## Limits

- Pad placement inside multi-cycle instructions is PRM-approximate
  (totals are exact); nothing in the project's oracle contracts
  intra-instruction bus phase placement beyond the documented totals and
  the boundary model.
- The $E000 control port, the trigger engine and the done marker live in
  the test harness, not the core (ASSUMPTION M6800-A4).
- Unassigned-opcode behavior follows the oracle's NOP convention
  (ASSUMPTION M6800-A2); real-silicon behavior is undefined there.
